# API 사용 기록

이 기능은 업무 API의 사용량과 상태를 파악하기 위한 메타데이터이며 보안 감사 로그나 쿼터 집행 기능이 아닙니다.

## 수집 범위

- 기존 업무 경로(`auth`, `users`, `students`, `teachers`, `clubs`, `meals`, `notices`, `study-supervisors`, `timetables`)에서 서블릿에 도달한 최초 요청을 관찰합니다. 성공, 애플리케이션 오류, 인증·인가 거절을 포함합니다. 기존 업무 경로 아래에서 컨트롤러가 결정되지 않은 거절·미매핑 요청은 `UNMAPPED`로 기록합니다. 새 업무 경로를 추가할 때 수집 대상도 함께 검토합니다.
- CORS 프리플라이트, Swagger/OpenAPI, 헬스 등 업무 밖 경로, 이 기록을 읽는 운영용 관리자 API는 기록하지 않습니다. Tomcat 오류 재디스패치를 별도 행으로 세지 않습니다. 컨테이너가 애플리케이션에 전달하기 전에 거절한 요청은 관찰할 수 없습니다. 현재 동기식 MVC 업무 요청을 대상으로 합니다.
- 저장·조회 필드는 `id`(서버 생성 정수), `occurredAt`(UTC의 응답 완료 시각), `method`(정해진 HTTP 메서드 또는 `OTHER`), `route`(MVC가 정한 템플릿 또는 `UNMAPPED`), `status`(최종 상태), `durationMs`(기록 자체의 DB 시간을 뺀 처리 시간, 밀리초)입니다. 모두 필수이며 null을 반환하지 않습니다.
- 요청·응답 본문, raw URI/쿼리/헤더 값, 경로 변수 값, IP, 사용자 식별자, 이메일, 비밀번호, OTP, 토큰과 API 키 원문·해시를 저장하지 않습니다.
- 수집 범위는 MVC와 같은 방식으로 해석한 첫 경로 세그먼트로 결정합니다. 같은 업무 경로의 percent 인코딩 표기에서도 원문이나 디코딩된 값 대신 MVC 템플릿 또는 `UNMAPPED`만 저장합니다.
- 요청 완료 시 메타데이터를 메모리 큐에 넘깁니다(`api-usage-log.queue-capacity`, 기본 256건, 허용 1–4096건). 요청 스레드는 큐 공간이나 DB를 기다리지 않습니다. 기록 워커 한 개가 별도 트랜잭션으로 한 번만 저장을 시도합니다. 저장 실패는 `API_USAGE_LOG_WRITE_FAILED`, 포화로 버린 건수는 워커가 진행할 때 `API_USAGE_LOG_QUEUE_FULL`로 알립니다. 종료 시 큐에 남은 기록은 버릴 수 있습니다(`API_USAGE_LOG_SHUTDOWN_DROPPED`). 신호에 요청 값이나 예외 메시지는 포함하지 않습니다. 조회에는 아직 저장되지 않은 기록이 보이지 않을 수 있고, 재시도·백필은 없습니다. 기록 워커는 공용 데이터소스에서 한 번에 최대 한 연결을 사용합니다.

## 관리자 조회

`GET /admin/api-usage-logs` (자동 HEAD 포함): ADMIN 액세스 JWT만 허용합니다. 토큰 없음/무효는 `401 INVALID_TOKEN`, USER는 `403 FORBIDDEN`입니다.

- `from`, `to`: ISO 8601의 시각. 둘 다 생략하면 조회 시점 기준 최근 24시간입니다. 함께 지정하면 `from` 포함, `to` 제외이며 최대 31일입니다. 허용 경계는 `1970-01-01T00:00:00Z` 이상, `9999-01-01T00:00:00Z` 이하입니다.
- `method`: `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`, `TRACE`, `CONNECT`, `OTHER` 중 하나이며 생략하면 전체입니다.
- `status`: 100–599의 정수이며 생략하면 전체입니다.
- `page`: 0–1000(기본 0). `size`: 1–100(기본 20). `occurredAt` 내림차순, 동일 시각이면 `id` 내림차순입니다. 응답은 기존 `content`, `page`, `size`, `totalCount`, `totalPage` 형식입니다. 연속 페이지 조회 시 `from`/`to`를 고정해도 동시 기록이 들어오면 오프셋이 달라질 수 있습니다.
- 범위·타입 오류는 조회 트랜잭션 전에 `400 INVALID_INPUT`을 반환합니다. 연결 획득을 포함한 조회 저장소 오류는 `500 INTERNAL_SERVER_ERROR`, 잠금 충돌은 기존대로 `409 CONCURRENT_UPDATE`입니다.

## 적용 및 롤백

1. 보존기간, 테이블 성장·접근 점검 주기, 기록 실패 알림 처리 주체와 허용 지연을 운영 팀이 결정합니다. 이 PR은 자동 삭제나 무기한 보존 정책을 만들지 않습니다.
2. 앱은 기본 `ddl-auto=validate`라 기동 전에 별도 승인으로 [신규 MySQL 테이블 DDL](schema/api_usage_logs.sql)을 먼저 적용해야 합니다. 신규 테이블 생성만 수행하며 기존 테이블은 변경하지 않습니다. 과거 요청의 백필은 없습니다. 기존 앱은 새 테이블을 사용하지 않습니다.
3. 적용 후 관리자의 접근 제한, 기록률·DB 지연과 테이블 성장, 저장 실패와 큐 포화 신호를 확인합니다. 복구 시 먼저 이전 앱으로 되돌리고 테이블은 유지합니다. 삭제가 필요한 경우 보존 정책과 데이터 삭제 승인을 별도로 받습니다.
