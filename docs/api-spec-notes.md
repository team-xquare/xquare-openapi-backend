# API 명세 검토 메모

`docs/openapi.yaml`을 노션 "xquare open API"의 API 명세서(38개)와 기능 명세서(31개)로 만들면서 확인한 것들입니다.

- **명세 충돌**: 두 명세서가 다른 곳입니다. 모두 API 명세서를 따랐고, 무엇을 골랐는지 함께 적었습니다.
- **빈 곳**: 두 명세서 어디에도 없어서 구현 전에 정해야 하는 것입니다. YAML에는 넣지 않았습니다.

공통으로 반복되는 빈 곳:
- 입력 검증 실패(필수값 누락, 형식 오류, 길이 초과)의 HTTP 상태와 에러 코드가 대부분 없습니다. 회원가입·로그인·재발급만 현재 구현에 맞춰 `400 INVALID_INPUT`을 넣었습니다.
- PATCH가 부분 수정인지 전체 교체인지, 생략한 필드와 `null`을 어떻게 처리하는지가 정해지지 않았습니다.
- 목록 조회의 정렬 기준과 `page`/`size` 범위 위반 시 응답이 없습니다.
- 에러 응답 `message` 문구는 정의돼 있지 않아서, 예시에는 노션의 에러 설명을 옮겨 적었습니다.
- 급식 조회는 공개(ALL) API인데 노션 에러 표에 `401 INVALID_TOKEN`이 있습니다. 401을 내지 않기로 정하고 YAML에서 뺐습니다(#21, 아래 급식 항목).

# 인증/인가

### 명세 충돌
- 회원가입 기본 권한: 기능 명세서 `MEMBER` / API 명세서 `USER` / 채택: `USER`
- 오류 코드 표기: 기능 명세서 `OtpNotFound`, `OtpMismatch`, `EmailNotVerified`, `UsernameAlreadyExists` (PascalCase 예외명) / API 명세서 `OTP_NOT_FOUND`, `OTP_MISMATCH`, `EMAIL_NOT_VERIFIED`, `USERNAME_ALREADY_EXISTS` / 채택: API 명세서의 UPPER_SNAKE_CASE
- 기능명 표기: 기능 명세서 "토큰 재발급" / API 명세서 "access token 재발급" / 채택: summary는 기능 명세서의 "토큰 재발급", 경로·필드는 API 명세서 기준
- 기능 명세서(토큰 재발급)는 상세기능이 "토큰을 재발급한다" 한 줄뿐이고 나머지는 템플릿 문구; 충돌 없음, API 명세서 내용만 사용

### 빈 곳
- 회원가입 400 INVALID_INPUT: API 명세서에 없음. 현재 구현 기준으로만 추가함
- OTP 발송/검증의 요청 값 검증 실패 시 응답(상태 코드/에러 코드) 미정의. 특히 otp 6자리 형식 위반, email 형식 위반(검증 API)
- 로그인·재발급 필드 누락: 명세에 없어 회원가입과 같은 `400 INVALID_INPUT`으로 정함(#10)
- 로그인 계정 잠금(ACCOUNT_LOCKED)의 해제 조건 및 잠금 기간 미정(기능 명세서에도 "미정"으로 기재). 정해질 때까지 구현하지 않기로 함(#10)
- 로그인 실패 횟수 카운트 기준(누적/연속, 초기화 시점, 아이디 기준 여부) 미정
- 오류 응답의 message 문구: 두 명세서 모두 정의하지 않아 YAML의 message 예시는 설명을 한국어로 옮긴 임의 문구임
- OTP 재발송 제한(횟수/쿨다운), 기존 OTP 덮어쓰기 여부, OTP 검증 실패 횟수 제한 미정
- 회원가입 시 학번 중복 처리 규칙 및 에러 코드 미정 (이메일 중복은 PR #3 리뷰에서 `409 EMAIL_ALREADY_EXISTS`로 정함)
- emailVerifiedToken 사용 후 삭제(1회용) 여부 미정
- 회원가입 name 길이: 명세에 없어 PR #3 리뷰에서 1~10자로 정함
- 회원가입 password 문자 종류: 명세에 없어 공백을 뺀 ASCII(`\x21-\x7E`)로 정함. BCrypt가 72바이트를 넘는 비밀번호를 거부하는데, 글자 수 제한만으로는 이모지 등 멀티바이트 문자를 막지 못하기 때문
- 토큰 만료 시간(access/refresh TTL), 토큰 형식(JWT 클레임) 미정. 구현은 access 1시간, refresh 14일(환경변수로 변경 가능), 클레임은 CLAUDE.md의 JWT 항목 참고
- 재발급 시 refreshToken 저장 방식과 동시 요청 처리: 명세에 없어 Redis `refresh_token:{userId}`에 사용자당 하나만 두고, 재발급은 저장값이 요청 토큰과 같을 때만 바꾸도록(compare-and-set) 정함(#10). 그래서 다른 기기에서 로그인하면 먼저 로그인한 기기는 재발급에 실패함(사용자가 정함)
- 오류 응답 500 EMAIL_SEND_FAILED 외 서버 내부 오류 공통 처리 미정
- 회원가입 password의 "특수문자" 허용 문자 집합 미정 (YAML에는 minLength/maxLength만 반영)
- 로그인 password 길이/형식 위반 시 INVALID_CREDENTIALS인지 검증 오류인지: 명세에 없어 빈 값만 `400 INVALID_INPUT`, 나머지는 `401 INVALID_CREDENTIALS`로 정함(#10). 형식 규칙이 바뀌어도 기존 계정이 로그인할 수 있게 하려는 것

# 학생·교직원

### 명세 충돌
- 항목: 학생 등록/수정 입력 필드 `동아리` / 기능 명세서: UI 입력창에 동아리 포함 / API 명세서: 동아리는 이 API에서 다루지 않음(동아리 등록·수정의 `member`로만 변경) / 채택: API 명세서 (요청 body에 club 없음)
- 항목: 교직원 등록/수정 입력 필드 `담당 동아리` / 기능 명세서: 입력창에 포함, 누락 시 `담당 동아리을 선택해 주세요.` / API 명세서: 이 API에서 다루지 않음(동아리 등록·수정의 `teacher`로만 변경) / 채택: API 명세서
- 항목: 교직원 `담당 학급` 누락 예외 / 기능 명세서: 누락 시 `담당 학급을 입력해 주세요.` / API 명세서: `grade`, `classNum`은 담임이 아니면 null 허용 / 채택: API 명세서 (grade, classNum nullable, 등록 required에서 제외)
- 항목: 학생 조회 결과 없음 / 기능 명세서: `해당 학생은 없습니다.` 반환 / API 명세서: 404 `STUDENT_NOT_FOUND` (존재하지 않는 학생 id) / 채택: API 명세서
- 항목: 인증 누락 / 기능 명세서: `로그인이 필요한 서비스입니다.` / API 명세서: 401 `INVALID_TOKEN` / 채택: API 명세서
- 항목: 교직원 삭제 대상 없음 / 기능 명세서: `이미 삭제되었거나 존재하지 않는 정보니다.` / API 명세서: 404 `TEACHER_NOT_FOUND` / 채택: API 명세서
- 항목: 학생 삭제 대상 없음 / 기능 명세서: 이미 삭제된 학생 / API 명세서: 404 `STUDENT_NOT_FOUND` / 채택: API 명세서
- 항목: 항목 누락 예외(학생 등록/수정, 교직원 등록/수정) / 기능 명세서: 각 항목 누락을 예외로 명시 / API 명세서: 누락에 대한 에러 코드 없음 / 채택: 학생·교직원 등록 request의 필수 필드를 `required`로 표시(교직원은 grade/classNum 제외), 에러 응답은 추가하지 않음
- 항목: 필드 구성 / 기능 명세서: 학생 조회 응답 "학년/반/번호" 등 설명 / API 명세서: studentNumber + 파생값 grade/classNum/number / 채택: API 명세서

### 빈 곳
- 필드 누락·형식 오류(이름 공백, 잘못된 birthDate 형식, `@dsm.hs.kr` 아닌 이메일, 잘못된 enum 값, 범위 밖 grade/classNum 등)의 에러 코드와 HTTP status가 없음 (INVALID_STUDENT_NUMBER 외 400 코드 없음)
- 학생 수정/교직원 수정 PATCH의 부분 수정 여부 불명: 모든 필드 선택으로 표기했고, 미전송 필드 처리와 교직원 grade/classNum에 null 전송 시 "해제"인지 "미변경"인지 정의 없음
- 기능 명세서의 `수정된 내력이 없습니다.`(변경 없음) 처리 방식과 에러 코드 없음
- 교직원 등록/수정에서 name, office, 학생 name의 길이 제한·공백 규칙 없음
- 교직원 grade/classNum 허용 범위(1~3, 1~4)는 예시일 뿐 제약 여부 불명, 한쪽만 null인 경우 허용 여부 불명
- 학생 name, 교직원 name 조회 필터: 학생은 부분 일치로 명시, 교직원 name은 일치 방식 미명시 (grade/classNum/subject는 정확 일치로 추정)
- 목록 조회의 정렬 기준, page/size 범위 위반(size>100, page<0) 시 동작과 에러 코드 없음
- 목록 조회 필터를 여러 개 줬을 때 AND 결합인지 명시 없음 (AND 추정)
- 학생·교직원 삭제 시 소속 동아리 member/teacher 연관 처리, 소프트/하드 삭제 여부 없음
- 학생 등록 시 같은 이메일 중복 처리, 이메일·생일 유니크 여부 없음
- 학번-학년/반/번호 파생 규칙은 서술되어 있으나 번호(마지막 2자리) 범위(00 허용 여부) 불명
- 등록/삭제/수정 응답의 `message`는 고정 한국어 문자열(생성되었습니다./수정되었습니다./삭제되었습니다.)이며 별도 응답 DTO 규약 없음
- 학생 조회/전체조회의 403 여부: USER 권한이라 FORBIDDEN 미정의. 교직원 등록의 ADMIN 외 사용자 응답은 403으로 문서화
- 학생 등록 시 `Location` 외 생성된 id를 body로 돌려주는지 여부 (body는 message만)
- 교직원 조회 응답의 `club`, 학생 응답의 `club` 형식은 CLUB 타입(id, name, logo)으로만 기술되며 nullable 표기는 설명에서만 확인됨
- 인증 방식(Bearer JWT)과 role 판별 방식은 페이지에 없음 (공유 securityScheme 가정)

### 구현하면서 정한 것 (학생)
- 수정(PATCH)은 등록과 같은 모든 필드를 받아 통째로 바꾼다. 부분 수정은 하지 않는다. 명세 예시 body도 모든 필드를 담고 있다.
- 입력 검증 실패(필수 값 누락, 이름 공백·10자 초과, `@dsm.hs.kr`이 아닌 이메일, 날짜 형식 오류)는 `400 INVALID_INPUT`. 학번 범위만 `INVALID_STUDENT_NUMBER`.
- 학번은 명세대로 1000~3999 범위만 본다. 반이 0이거나 번호가 00인 학번(예: 2000)도 받는다.
- 목록은 학번 순. 조건은 AND로 묶는다. `page`가 0~21474836 밖이거나 `size`가 1~100 밖이면 `400 INVALID_INPUT`. `page` 상한은 offset(page × size)이 int를 넘지 않게 하려는 것이다.
- 검색 `grade`는 1~3, `classNum`은 0~9만 받고 벗어나면 `400 INVALID_INPUT`. 학번 1000~3999에서 나올 수 있는 값이다. 막지 않으면 큰 값에서 쿼리의 `grade * 1000`이 넘쳐 500이 났다.
- 이름 부분 일치 검색에서 `%`, `_`는 와일드카드가 아닌 글자 그대로 찾는다.
- 이메일 중복은 막지 않는다. 명세에 에러 코드가 없다.
- 삭제는 실제로 지운다(하드 삭제). 같은 학생을 동시에 지우면 하나만 200이고 나머지는 `404 STUDENT_NOT_FOUND`.
- 응답의 `club`은 소속 동아리(id, name, logo), 없으면 null(#25). 학생 수정으로는 바뀌지 않는다.
- 동아리 구성원인 학생을 지우면 구성원에서 빠지고, 팀장이면 그 동아리의 `manager`가 null이 된다(#25, 아래 동아리 항목).

### 구현하면서 정한 것 (교직원)
- 수정(PATCH)은 학생과 같이 모든 필드를 받아 통째로 바꾼다. 그래서 `grade`, `classNum`을 null로 보내면 담임에서 빠진다.
- `grade`와 `classNum`은 함께 보내거나 함께 비워야 한다. 범위는 학번 규칙에 맞춰 학년 1~3, 반 1~9. 어기면 `400 INVALID_INPUT`.
- 이름은 1~10자, 교무실은 1~30자. 어기면 `400 INVALID_INPUT`.
- 검색에서 이름은 정확히 일치, 교무실만 부분 일치. 명세가 교무실에만 부분 일치라고 적었다. 교무실의 `%`, `_`는 글자 그대로 찾는다. 목록은 등록 순(id).
- 같은 교직원을 동시에 지우면 하나만 200이고 나머지는 `404 TEACHER_NOT_FOUND`.
- 같은 학급의 담임이 여러 명이어도 막지 않는다. 명세에 에러 코드가 없다.
- 응답의 `club`은 담당 동아리(id, name, logo), 없으면 null(#25). 담당 교직원을 지우면 그 동아리의 `teacher`가 null이 된다.

# 일정·자습 감독

### 명세 충돌
- 일정 등록/수정 입력 대상: 기능 명세서는 "컴시간 시간표 + 나이스 학사 일정 + 자습 감독"을 월/연도 단위로 입력받는다고 서술 / API 명세서는 학사 일정 1건(date, title, content)만 등록·수정 / 채택: API 명세서
- 일정 조회: 기능 명세서는 "학교 통합 일정 조회"(시간표+학사 일정+자습 감독, 월/연도 입력) / API 명세서는 단건 `GET /schedules/{scheduleId}`뿐이며 통합·목록 엔드포인트 없음 / 채택: API 명세서, 통합 조회는 만들지 않음(API 페이지에도 시간표 API 확정 후 별도 추가 필요하다고 명시)
- 자습 감독 분류: 기능 명세서는 페이지 구분 `교직원` / API 명세서는 구분 `자습 감독`, 경로 `/study-supervisors` / 채택: tag `자습 감독`
- 자습 감독 조회: 기능 명세서는 단일 "정보 조회"(날짜, 층, 담당 선생님 배열) / API 명세서는 기간 조회 `GET /study-supervisors`와 일별 조회 `GET /study-supervisors/day` 두 개 / 채택: API 명세서
- 에러 표시: 기능 명세서는 메시지 문구(`로그인이 필요한 서비스입니다.`, `이미 삭제되었거나 존재하지 않는 정보입니다.`, `수정된 내력이 없습니다.`) / API 명세서는 에러 코드 / 채택: 코드 기준, 메시지는 API 페이지의 한국어 설명 사용
- 기능 명세서에서 추가 반영한 내용: 일정 삭제의 NEIS 일정 삭제 불가 사유(다음 동기화 때 재생성). 그 외 기능 명세서는 API 명세서보다 정보가 적음

### 빈 곳
- 통합 일정 조회(시간표+학사 일정+자습 감독)와 일정 목록/월·연도별 조회 엔드포인트 없음. 시간표 API 미확정

# 급식·동아리·공지

### 명세 충돌
- 공지 목록 조회 페이지네이션 파라미터: 기능 명세서 `page`, `limit`, 기본값 page 0 / limit 10 | API 명세서 `page`, `size`, 기본값 page 0 / size 20, 최대 100 | 채택: API 명세서

- 공지 등록/수정 입력 항목: 기능 명세서 UI에 `작성일` 입력창 존재 | API 명세서 요청 바디는 `title`, `content`만, 작성자는 토큰에서 자동 설정 | 채택: title, content만

- 인증 누락 처리: 기능 명세서 메시지 "로그인이 필요한 서비스입니다." | API 명세서 `INVALID_TOKEN` 401 | 채택: INVALID_TOKEN 401 (message 문구는 API 명세서에 없어 YAML 예시에 "토큰이 없거나 유효하지 않음" 사용)
- 동아리 입력 항목: 기능 명세서 이름/로고/부장/구성원/사용실 (지도교사는 조회 설명에만) | API 명세서 `teacher` 추가, `manager`는 학생 id | 채택: API 명세서
- 공지 삭제 404 메시지: 기능 명세서 "이미 삭제되었거나 존재하지 않는 공지사항입니다." | API 명세서 "이미 삭제되었거나 존재하지 않는 공지 id" (공지 수정 페이지는 "존재하지 않는 공지 id") | 채택: API 명세서
- 공지 제목/본문 길이(100/4000자)와 필수 여부는 API 명세서에 없어 기능 명세서 값으로 보강(충돌 아님, 스키마 maxLength/required 및 description에 명시)

### 구현하면서 정한 것 (급식, #21)
- 등록·수정 요청의 `date`, `breakfast`, `lunch`, `dinner`는 모두 필수. 급식이 없는 끼니는 빈 배열로 보낸다.
- '급식 없음' 표시(명세에 없음, 성준님 확인 필요): 명세에 급식 삭제가 없어서, 나이스가 만든 급식을 관리자가 없앨 방법으로 정했다(#24 리뷰).
  - 세 끼가 모두 빈 배열인 행이 '급식 없음' 표시다(`edited_by_admin = true`). 월간 조회의 `meals`·`totalCount`에서 빠지고, 단건 조회·수정은 `404 MEAL_NOT_FOUND`. 나이스 동기화는 관리자 행을 건너뛰므로 그 날짜를 다시 만들지 않는다.
  - 수정(PATCH)으로 세 끼를 모두 빈 배열로 보내면 그 급식이 표시로 바뀐다. 등록(POST)도 세 끼 모두 빈 배열을 받아, 나이스 급식이 들어오기 전에 그 날짜를 미리 막을 수 있다(201, `Location`의 id는 단건 조회 404).
  - 표시는 없는 급식으로 본다. 표시된 날짜에 등록하면 409 대신 그 행을 새 메뉴로 바꾸고 201(`Location`은 그 행의 id). 표시된 날짜로 수정해 옮기면 표시를 지우고 옮긴다.
  - 수정으로 날짜를 옮기면 원래 날짜에 표시를 남긴다. 비워 두면 다음 동기화가 같은 나이스 급식을 원래 날짜에 다시 만들어, 같은 급식이 두 날짜에 생기기 때문이다. 대신 그 날짜는 이후 나이스에 급식이 올라와도 반영되지 않는다(관리자가 등록하면 된다).
- 메뉴는 끼니마다 20개까지, 하나에 1~50자. 공백만 있거나 줄바꿈 같은 제어 문자가 있으면 `400 INVALID_INPUT`. 메뉴 목록은 DB에 JSON 배열 문자열로 저장한다.
- 수정(PATCH)은 학생·교직원처럼 모든 필드를 받아 통째로 바꾼다. 다른 급식이 있는 날짜로 바꾸면 `409 MEAL_ALREADY_EXISTS`(수정 에러 표에 없지만 등록과 같은 코드). 날짜를 그대로 두는 수정은 된다.
- 월간 조회 `startDate`/`finishDate`는 선택. 둘 다 생략하면 이번 달 1일~말일(기능 명세서의 "현재 월", 서울 시간 기준). 하나만 주면 그 날짜가 속한 달의 1일 또는 말일로 채운다. 응답의 `startDate`/`finishDate`는 채운 실제 기간이다.
- 조회 기간은 시작일·종료일을 포함해 최대 92일. `finishDate`가 `startDate`보다 이르거나 92일을 넘으면 `400 INVALID_DATE_RANGE`. 같은 날짜(하루)는 된다. 날짜 형식 오류는 `400 INVALID_INPUT`.
- 월간 조회는 날짜 순. `totalCount`는 `meals` 개수.
- 공개 API(월간 조회, 단건 조회)는 토큰이 없거나 유효하지 않아도 401 없이 조회한다. 공개 API에서 만료된 토큰 때문에 실패할 이유가 없어서다. YAML의 401 응답은 뺐다.
- 나이스 연동: 급식식단정보(`mealServiceDietInfo`)를 매일 04:00(서울 시간, `NEIS_MEAL_SYNC_CRON`)에 이번 달·다음 달 월 단위로 가져와 날짜별로 저장한다. 학교는 대덕소프트웨어마이스터고(교육청 `G10`, 학교 `7430310`, schoolInfo API로 확인).
  - `DDISH_NM`은 `<br/>`로 나누고 끝의 알레르기 번호 괄호(`배추김치 (9)`의 ` (9)`)는 지운다. 명세 예시가 메뉴 이름만 담고 있고 응답에 알레르기 필드가 없어서다. 메뉴 이름 안의 괄호(`깻잎찜(오븐)`)는 남긴다.
  - `MMEAL_SC_CODE` 1·2·3만 조식·중식·석식으로 쓰고 나머지는 버린다.
  - 관리자가 등록하거나 수정한 날짜는 동기화가 덮어쓰지 않는다. 관리자가 고치는 건 나이스 정보가 틀렸거나 없을 때라서, 다음 날 동기화가 되돌리면 안 되기 때문이다. 대신 그 날짜는 이후 나이스가 바뀌어도 반영되지 않는다.
  - 나이스에서 사라진 날짜의 급식은 지우지 않는다. 데이터가 없으면(`INFO-200`) 그 달은 건너뛴다.
  - 결과 코드가 `INFO-000`·`INFO-200`이 아니거나, 결과 코드도 급식 목록(`row`)도 없는 응답이면 그 달 동기화를 실패로 보고 경고 로그를 남긴다. 0건으로 성공 처리하지 않는다.
  - `NEIS_API_KEY`가 없으면 동기화를 건너뛰고 경고 로그만 남긴다(앱은 뜬다). 키 없이 부르면 나이스가 샘플 5건만 주기 때문이다.

### 구현하면서 정한 것 (동아리, #25)
- `room` 값: 명세에 예시(`ROOM_2_1`, `ROOM_2_2`)만 있어서 같은 형식 `ROOM_{층}_{실 번호}`로 1~5층, 1~9실(45개)을 뒀다. 목록에 없는 값은 `400 INVALID_INPUT`. DB `clubs.room` 컬럼은 MySQL enum이라(`docs/schema/clubs.sql`) 값을 더하거나 바꾸면 `ClubRoom`과 함께 `ALTER TABLE`로 컬럼 목록도 맞춰야 한다. 이미 저장된 값을 지우거나 이름을 바꾸면 그 행을 읽을 때 500이 나므로, 운영 데이터가 생기기 전에 실제 실 목록을 확정해야 한다.
- 등록·수정 요청의 `name`, `logo`, `room`, `manager`, `member`는 필수이고 `teacher`만 생략·null 가능. `name`은 1~20자, `logo`는 1~255자, `member`는 최대 50개. 어기면 `400 INVALID_INPUT`. `member`에 null이 섞여도 `400 INVALID_INPUT`.
- 동아리 이름 중복은 막지 않는다. 명세에 에러 코드가 없다.
- `logo`는 파일 업로드 API가 없어서 키가 실제로 있는지는 보지 않는다.
- `member`에 같은 id가 여러 번 있으면 한 번으로 친다. 빈 목록은 팀장이 없으므로 `400 MANAGER_NOT_IN_MEMBER`.
- 한 학생은 한 동아리에만 속한다(학생 응답의 `club`이 객체 하나). 다른 동아리 소속 학생을 `member`에 넣으면 `409 STUDENT_ALREADY_IN_CLUB`(새 코드). 자동으로 옮기지 않는 것은, 옮기면 원래 동아리의 팀장이 구성원에서 빠질 수 있어서다.
- 한 교직원은 한 동아리만 담당한다(교직원 응답의 `club`이 객체 하나). 다른 동아리 담당 교직원을 넣으면 `409 TEACHER_ALREADY_IN_CLUB`(새 코드).
- 수정(PATCH)은 학생·교직원처럼 등록과 같은 필드를 모두 받아 통째로 바꾼다. `teacher`를 null로 보내거나 빼면 담당 선생님이 없어진다. `member`는 명세대로 전체 교체하고, 빠진 학생은 소속이 없어진다.
- `ROOM_ALREADY_IN_USE`·`STUDENT_ALREADY_IN_CLUB`·`TEACHER_ALREADY_IN_CLUB`는 다른 동아리와 겹칠 때만 낸다. 수정하면서 자기 교실·구성원·담당 선생님을 그대로 두는 것은 된다.
- 검사 순서: 입력 형식(400) → (수정) 동아리 존재(404) → 팀장 포함(400) → 학생·교직원 존재(404) → 교실(400) → 학생 소속(409) → 교직원 담당(409).
- 동시 등록·수정으로 교실·교직원 검사를 통과해도 unique 제약(`uk_clubs_room`, `uk_clubs_teacher`)에 걸리면 같은 에러 코드로 바꾼다. 같은 학생을 동시에 다른 동아리에 넣지 못하게 구성원 학생 행을 잠그고 읽는다. 수정은 빠질 기존 구성원도 새 구성원과 한 번에 id 순으로 잠가, 요청끼리 잠금 순서가 엇갈려 데드락이 나지 않게 한다(#26 리뷰).
- 잠금 충돌(데드락, 잠금 대기 시간 초과)로 DB가 트랜잭션을 되돌리면 `409 CONCURRENT_UPDATE`("동시에 수정되어 처리하지 못했습니다. 다시 시도해 주세요.", 새 코드, 명세에 없음). `GlobalExceptionHandler`가 `PessimisticLockingFailureException`(`CannotAcquireLockException` 포함)을 받아 모든 API에서 같은 형식으로 준다. 처리 안 하면 `{code, message}` 형식 없는 500이 나간다. 어느 API에서나 날 수 있는 공통 응답이라 YAML의 API별 에러 표에는 넣지 않았다.
- 삭제는 실제로 지운다(하드 삭제). 학생·교직원은 지우지 않고 소속·담당 동아리만 null이 된다. 기능 명세서의 "동아리 변경 시즌 이후 기존 정보가 사라진다"는 별도 기능(일괄 초기화)이 없어서, 관리자가 동아리를 지우거나 수정하는 것으로 처리한다.
- 학생·교직원을 지우면 동아리는 남는다. 구성원 학생은 구성원에서 빠지고, 팀장 학생이면 `manager`가 null(새 팀장은 수정으로 정한다), 담당 교직원이면 `teacher`가 null. DB의 외래 키 `ON DELETE SET NULL`로 처리해서 학생·교직원 삭제 코드는 그대로다. 그래서 상세·목록 응답의 `manager`는 nullable이다.
- 검색: 동아리명은 부분 일치, 구성원 이름은 부분 일치(명세 예시가 `성준`, `민수`처럼 이름만 있다), 선생님 이름은 교직원 검색처럼 정확히 일치. `member`를 여러 개 주면 모두 구성원에 있는 동아리만 찾는다(AND, 다른 조건과도 AND). `member`는 최대 10개. `%`, `_`는 글자 그대로 찾는다. 결과가 없으면 빈 `content`.
- 목록은 등록 순(id), 구성원(`member`)은 학번 순. page/size 범위는 학생·교직원과 같다.
- 학생·교직원 응답의 `club`을 이번에 채웠다. 목록 조회는 학생은 소속 동아리를 같이 읽고(fetch join), 교직원·동아리는 페이지의 id를 모아 한 번 더 읽어서 쿼리 수가 페이지 크기와 상관없다(`ClubTest`가 쿼리 수를 센다).
